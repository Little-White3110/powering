## 1. 摘要

按「常态（用户什么都不做、屏幕亮着）」下的开销排序，本仓库有 **1 个主因 + 4 个放大器**：

| 级别 | 问题 | 位置 | 常态频率 | 是否默认开启 |
|---|---|---|---|---|
| **P0** | 呼吸灯效导致环窗口**逐帧重绘**（约 60fps 常驻） | `RingState.kt:726` + `RingState.kt:1252` | 60 次/秒，亮屏期间不间断 | 是（`breathingEnabled=true`、`breathingOnIdle=true`） |
| **P0** | 每帧构造 50 字段 `signature()` 字符串（含两条列表编码流水线） | `RingState.kt:410-432`、`RingState.kt:1231` | 60 次/秒 | 是（与开关无关，绘制入口第一步） |
| **P1** | 系统反色动画期间，同一帧做 **3 次取色 / 2 次完整应用**，含 14 个反射字段读 | `BatteryColorHook.kt:144-155`、`:234-241`、`:251-266`、`RingState.kt:754-757` | 动画期间 60 次/秒 ×2-3 | 是 |
| **P1** | 逐帧重画几何：挖孔矩形、屏幕坐标、Resources 密度全部每帧重新解析 | `CutoutGeometry.kt:33-72`，`RingRenderer.kt:217-222` | 60 次/秒 | 是 |
| **P1** | 音乐播放状态轮询**不受开关门控**，每 1.2s 一次 AudioService binder 往返 | `BatteryObserver.kt:73-92`、`:221` | 0.83 次/秒 ≈ 7.2 万次/天 | 否（开关无关，恒跑） |
| **P2** | 5 个常驻定时器（400/600/600/1200/2000ms）在 SystemUI 主线程反复唤醒 | 见 §4 表 | 合计 ≈7.2 次/秒 | 是 |
| **P2** | 诊断日志 `traceEnabled` 从未关闭，反色动画期间每 60ms 写一行（logcat + `XposedBridge.log`） | `BatteryColorHook.kt:69`、`:362-377` | 动画期间最多 16 行/秒 | 是 |
| **P2** | 每条通知状态变化都 `commit()` 同步落盘 | `NotifStateBridge.kt:73-75` | 每条新通知 1 次 | 是（开了提醒即生效） |

一句话：**耗电的主因不是"读写"，而是"亮屏期间永不停歇的 60fps 重绘"，以及每帧顺带的字符串构造与反射取色**。真正的磁盘写入（prefs commit、日志）频率都在"事件级"，量级远小于帧循环。

## 2. P0-1 逐帧重绘是常态开销的主体

`RingState.needsContinuousAnimation()`：

```1252:1258:app/src/main/java/com/powerring/hole/ring/RingState.kt
        if (needsContinuousAnimation(c)) {
            view.postInvalidateOnAnimation()
        } else if (c.burnInProtection) {
```

判定链里最后一条命中默认配置：

```726:726:app/src/main/java/com/powerring/hole/ring/RingState.kt
        if (c.breathingEnabled && (chargingNow || c.breathingOnIdle)) return true
```

`RingConfig` 默认值（`RingConfig.kt:58`、`RingConfig.kt:60`；`ui/PrefsStore.kt:55-56` 同值）：`breathingEnabled = true`、`breathingOnIdle = true`。

**后果**：只要屏幕亮着，环窗口每一帧都 `postInvalidateOnAnimation` → SystemUI 每 VSYNC 走一遍绘制并参与合成。这个自续帧设计本身是对的（注释也明确写了"全部关闭或不在生效状态时返回 false，避免常态 60fps 空转"），问题在于**默认配置恰好让它常态命中**。

**关键失衡**：呼吸的视觉周期是 `BREATH_PERIOD_IDLE_MS = 3200L`（`RingRenderer.kt:41`），充电呼吸 1800ms。3.2 秒一圈的缓入缓出，肉眼上 10–15fps 与 60fps 无法区分。当前是**用 60fps 的代价渲染一个 0.3Hz 的动画**。

> 待真机确认：亮屏静置 1 分钟，`adb shell dumpsys gfxinfo com.android.systemui framestats` 是否持续累积帧；关闭「平时呼吸」后帧数是否归零。

## 3. P0-2 每帧构造配置签名字符串

绘制入口第一件事：

```1227:1237:app/src/main/java/com/powerring/hole/ring/RingState.kt
    fun onCutoutDraw(view: View, canvas: Canvas) {
        val c = config
        attachCutoutView(view)
        // 配置发生变化时补发一帧，使滑杆/颜色调节在静止状态下也即时可见
        val sig = c.signature()
        if (sig != lastConfigSig) {
```

`signature()`（`RingState.kt:410-432`）把约 **50 个字段插值拼成一个长字符串**，其中还内嵌两条列表编码：

- `CustomColors.encodeRanges(levelRanges)` → `joinToString` + 每元素字符串模板（`CustomColors.kt:42-43`）
- `PercentNodes.encode(percentNodes)` → `asSequence().filter().distinct().sorted().take().joinToString()`（`PercentNodes.kt:55-61`）——`sorted()` 会把序列整表物化再排序

随后 `sig != lastConfigSig` 还要对两个 600 字符级字符串做内容比较。

**每帧成本**：一个 StringBuilder、若干个中间字符串、一个最终大 String（Kotlin String 为 UTF-16，600 字符 ≈ 1.2KB），粗估 **2–4KB 临时对象/帧**；60fps 下 ≈ **120–240KB/s** 的分配速率，直接转成 SystemUI 进程的 GC 压力。

**为什么这是纯粹的浪费**：`RingConfig` 是不可变 data class，`HookPrefs.cached` 只在配置重载时整体换新引用（`HookPrefs.kt:141`、`HookPrefs.kt:59`）。也就是说**配置是否变化，用引用相等就能判定**：

```kotlin
if (c !== lastConfigRef) { ... }   // O(1)，零分配
```

签名机制的初衷（"滑杆调节在静止状态下也即时可见"）用引用比较完全成立——配置写入必然经 `HookPrefs.load()` 产生新对象。

## 4. P1 反射取色：同一帧最多跑 3 次读、2 次完整应用

三个 Hook 挂在同一条系统动画链上（`BatteryColorHook.kt:144`、`234`、`251`）：

| Hook 点 | 位置 | 触发时机 | 回调里做什么 |
|---|---|---|---|
| `DarkIconDispatcherImpl.applyDarkIntensity(F)` | `BatteryColorHook.kt:144-155` | 反色动画**每帧** | `onClockTick()`（限流日志）+ `publish(fromClock = true)` |
| `MiuiBatteryMeterView.onDarkChanged(...)` | `BatteryColorHook.kt:251-266` | 反色动画**每帧** | `publish()` |
| `MiuiBatteryMeterIconView.onDarkChangeInternal()` | `BatteryColorHook.kt:234-241` | 反色动画**每帧** | `publish()` |

每次 `publish()`：`resolveIcon()` → `read(icon)` 读 **14 个反射字段**（`BatteryColorHook.kt:386-414`）→ 构造 `SystemBatteryColors` → `copy()` → 交给 `RingState.setSystemBatteryColors()`。

去重挡不住：

```754:757:app/src/main/java/com/powerring/hole/ring/RingState.kt
    fun setSystemBatteryColors(colors: SystemBatteryColors) {
        val last = lastSystemColors
        if (last == colors) return
        lastSystemColors = colors
```

`fromClock` 是 data class 的构造参数（`BatteryPalette.kt:76`），**参与 `equals()`**。时钟路径给 `true`、View 路径给 `false`，两条路径即使 14 个字段值完全相同也被判为不等 → 每帧至少 **2 次完整应用**（`BatteryPalette` 新建 + `ArgbEvaluator.evaluate` 装箱 + `invalidateAll()`）。

而 `invalidateAll()` 自身也是每调用一次就 `synchronized` + `toList()` 分配一份快照（`RingState.kt:1282-1291`）。

**放大场景**：状态栏反色动画在任何底色变化时都会跑——滚动列表进出深色区域、打开通知面板、进出全屏。用户滑一下屏幕的整个过程里，这条链路以 60fps 重复。

> 顺带的正确性问题（同一处代码，一并记在这里）：`attachCutoutView()`（`RingState.kt:505-507`）不加锁 `add`，而 `invalidateAll()`（`RingState.kt:1286`）加锁 `remove`，二者可在不同线程并发操作同一个 `WeakHashMap` 支撑的 Set。这是线程安全隐患，不是性能问题，但改动这一带时应当顺手统一。

`MUSIC_POLL_MS = 1200L`（`BatteryObserver.kt:30`），在 `start()` 里无条件 `mainHandler.post(musicPollRunnable)`（`BatteryObserver.kt:221`），**永不停止、也从不读 `config.musicPulseEnabled`**。

## 8. P2 高频写入清点

按"写入"字面意义（磁盘 / IPC / 日志）逐条列：

### 8.1 磁盘

| 写入点 | 触发频率 | 位置 |
|---|---|---|
| `NotifStateBridge.save()` 用 **`commit()`**（同步落盘） | 每条新通知到达 / 提醒清零时 1 次；`publish()` 有布尔+时间戳去重，但新通知会重置时间戳必然穿透 | `NotifStateBridge.kt:73-75`，调用链 `RingNotificationListener.kt:110-127` |
| `PrefsStore` 各 setter 用 `commit()` + `chmod` ×3 + 广播 | **仅滑杆拖动结束时**（`onValueChangeFinished`）与开关切换 | `PrefsStore.kt:134-152`、`:188-216` |

设计说明：设置页写入这一条**没有问题**——`ConfigSlider` 明确把 `onChange`（只更新内存 state）和 `onCommit`（落盘）分开（`SettingsScreen.kt:2072-2085`），拖动过程零磁盘写入。这是本仓库里做得对的一处，列出来是为了避免优化时被误伤。

`NotifStateBridge.save()` 的 `commit()` 值得改：它写在**模块应用进程**（通知监听服务）里，重消息场景（群聊刷屏、下载进度类通知）能到每分钟几十次同步 flash 写入，而且是 `commit` 不是 `apply`。它读回的时机只有 `load()`——而实际应答路径 `NotifStateResponder` 已经改为优先用监听服务的实时状态（`RingNotificationListener.kt:169`），说明这份 prefs 更多是历史兜底。

### 8.2 日志（`XposedBridge.log` + logcat 双写）

`ModuleLog` 每条同时走 `XposedBridge.log()` 和 `android.util.Log`（`ModuleLog.kt:11-14`）。LSPosed 会把模块日志另外落盘（`/data/adb/lspd/log/`）——**这条需要真机确认后再决定是否计入磁盘写入预算**。

热路径上的日志：

| 位置 | 限流 | 常态频率 |
|---|---|---|
| `BatteryColorHook.onClockTick`（`BatteryColorHook.kt:362-377`） | 60ms | 反色动画期间最多 **16 行/秒**；注释写着"验证完在 Task 5 关掉"，`traceEnabled = true` 是默认值且从未关（`BatteryColorHook.kt:69`） |
| `RingState.setSystemBatteryColors` 跟随色日志（`RingState.kt:796-808`） | 1000ms | 1 行/秒，内含 5 次 `String.format("%08X")` |
| `RingRenderer` 诊断（`RingRenderer.kt:953-960`） | `diagLogged` 一次性 | 一次性 |
| `CutoutGeometry.logOnce`（`CutoutGeometry.kt:119-135`） | 最多 5 条 | 一次性 |

`traceEnabled` 这一条是唯一真正的"高频写"嫌疑，且它是**遗留诊断开关忘记关闭**，不是功能需要。

### 8.3 IPC / binder

| 通路 | 频率 | 位置 |
|---|---|---|
| 音频驱动音量广播（模块应用 → SystemUI） | 每 100ms 一条 `sendBroadcast`（`SEND_INTERVAL_MS`） → SystemUI 主线程 receiver → `invalidateAll` | `AudioReactiveService.kt:166-171`、`NotifStateBridge.kt:101-110` |
| `AudioReactiveService` 静音暂停后仍 40ms 一次 `isMusicActive` | **25 次/秒 binder**，且没有退避、不会自动停服务 | `AudioReactiveService.kt:113-131` + `:99-111`（`paused` 分支照样按 `CHUNK_MS` 重投） |
| `getActivePlaybackConfigurations` | 0.83 次/秒 | §6 |
| `KeyguardManager.isKeyguardLocked` | 0.83 次/秒 | §6 |

音频服务这一条值得单独注意：`paused` 分支在 `tick()` 里 return 前**没有把重投周期拉长**，`captureLoop` 仍按 40ms 重投（`AudioReactiveService.kt:109`）。设计意图是"靠 isMusicActive 轮询决定是否恢复，省电"（注释在 `:116`），实现效果是**麦克风停了，但换成 25Hz 的 binder 轮询**——省的是 DSP/录音功耗，花的是 CPU 唤醒。用户开着音频驱动但不听歌时，就是这个状态一直挂着（`SILENCE_PAUSE_MS = 45_000L` 之后进入，无退出条件）。

## 9. 已经做得对、不要动反向的地方

审计同时确认了这些设计是省电/省 CPU 的，优化时别误改：

1. **配置读取有 volatile 缓存**：`HookPrefs.get()` 只读内存（`HookPrefs.kt:59`），跨进程查询在专用 `HandlerThread` 上（`:52-56`、`:76-82`），绝不在绘制线程做同步 binder。启动期失败走有限退避表（`:50`），不会无限重试。
2. **`Paint` 全部是 object 级单例**（`RingRenderer.kt:100-133`），绘制时只改属性不新建；没有 `BlurMaskFilter`/`setShadowLayer` 这类会踢回软件渲染路径的开销。
3. **滑杆拖动不落盘**（`SettingsScreen.kt:2072-2085`），见 §8.1。
4. **息屏不产帧**：`needsContinuousAnimation` 与 `onCutoutDraw` 都以 `screenOn` 为第一道闸（`RingState.kt:709`、`:1244`）。
5. **帧循环有"静止即停"设计**：`needsContinuousAnimation` 全关时返回 false，只剩防烧屏 5 秒一唤醒（`RingState.kt:1254-1257`）。
6. **防烧屏是边界唤醒而非帧循环**（`scheduleBurnInShift` 只在格边界 postDelayed 一次）。
7. **诊断 Hook 有日志上限**：`MAX_DIAG_LINES = 120`（`ImmersiveProbeHook.kt:59`）、`CutoutGeometry.MAX_LOGS = 5`。

## 10. 不确定项 —— 必须真机取证后才能定权重

静态阅读无法给排序定案，以下四条要实测：

1. **环窗口到底吃掉多少 GPU/合成时间**。抓 `adb shell dumpsys gfxinfo com.android.systemui framestats`，对比「呼吸开 / 呼吸关」两种状态下的帧数与 jank 比例。
2. **`XposedBridge.log` 是否落盘、单次成本**。用 `adb shell simpleperf record -p <systemui pid>` 采样 60 秒，看 `XposedBridge.log` / `StringBuilder` / `getDeclaredField` 在火焰图里的占比。
3. **息屏/Doze 期间 5 个定时器是否真被系统批量延后**。`adb shell dumpsys deviceidle` + `android.util.Log` 打点时间戳差值。
4. **整机层面的真实电流差**。`adb shell dumpsys batteryproperties` / `batterystats` 对比开关模块前后（或 `ringEnabled` 开/关）的 `ScreenOn` 期电流。

## 11. 建议的优化顺序（只列方向，不动代码）

按「收益 / 风险 / 改动量」给的优先级，等 §10 的实测数据回来再定具体方案与是否采纳：

1. **`signature()` 改引用比较**（§3）——一行改动，消除每帧 2–4KB 分配，零行为风险。
2. **反色取色三合一**（§4）——`fromClock` 移出 `equals`（或改为每帧只在时钟路径 `publish`，View 路径与它做同帧去重），`publish` 前按 `SystemClock.uptimeMillis()` 做同帧合并。
3. **挖孔几何缓存**（§5）——attach 时解析一次，失效绑到 `onOrientationChanged` 与 insets 派发。
4. **所有轮询与 Hook 安装以 `config.ringEnabled` 门控**（§6、§7）——关掉总开关应当让模块彻底静默，这也是"不拖垮 SystemUI"这条最高优先级原则的直接体现。
5. **呼吸/闪烁动画降帧**（§2）——给 `needsContinuousAnimation` 的自续帧加节流（如按动画最快视觉变化率取 15–20fps），或改用 `Choreographer` + 时间步长。这是收益最大的一条，但**也是观感风险最大的一条**，必须用户真机验收。
6. **关掉 `traceEnabled`**（§8.2）——遗留诊断，直接置 false。
7. **`NotifStateBridge.save` 的 `commit()` 改 `apply()` 或去掉**（§8.1）。
8. **音频服务暂停态退避**（§8.3）——`paused` 时把重投周期从 40ms 提到 1–2s，或长时间静音后 `stopSelf()`。
